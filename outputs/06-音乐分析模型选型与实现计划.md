# LOW END LAB：真实音乐分析的模型选型与实施计划

版本 0.2 · 核查日期 2026-11-08（北京时间）。本文件是技术选型与接入计划，不是已经运行模型得出的准确率报告。当前原型已修正 21 品与音点文字；本轮未下载大型权重、未调用收费推理、未上传用户音频。

## 后续实施记录（v0.3，2026-11-08）

第一阶段已落地：使用 Beat This! small0 进行真实拍点推理，结构采用明确标注的声学频谱变化基线，已接通本地上传、波形、原曲同步回听、段落循环与人工校正。此次没有运行 all-in-one 或音乐大语言模型；下文仍是完整路线规划，当前实施结果见《07-真实音频分析开发与结果.md》。

## 1. 推荐决策

第一条产品路线：**Qwen3.8-Omni-Flash 云端音频理解与教学解释 + 专用音乐信息检索（MIR）工具 + 现有确定性乐理/指板引擎**。

选择它作为接入首测候选的理由是当前官方接口支持音频输入、文本输出与工具调用，适合中文交互和服务化。这里没有证据证明它在贝斯逐音转录或和弦识别上优于专用模型，必须用我们的曲目集评测。[R01]

自行部署路线：**Qwen3-Omni-30B-A3B-Instruct**。官方仓库有 Music Analysis 示例，提供音频输入、文本输出、Transformers/vLLM 与 API 的部署说明。它是全模态模型，不是只针对音乐训练的模型。[R02]

音乐领域研究路线：**NVIDIA Music Flamingo**，官方分支给出的模型标识为 `nvidia/music-flamingo-hf`。它对和声、结构、音色、歌曲理解的定位最贴近本产品，但本次核读的版本明确是 preview、只供非商业研究。适合研究对照，不能因为代码开放就直接作为可商用产品依赖。[R03]

建议先建立可替换 provider 接口，不做微调，不从零训练音乐语言模型。只有实际评测证明中文解释、音乐判断或延迟有瓶颈时，再决定是否拆分教学模型或微调。

## 2. 为什么不能只接一个“会听音乐的大模型”

用户要的是与音乐同步、可用于演奏的数据。下列能力有不同的输出与验证方式：

| 用户问题 | 必须得到的证据 | 承担职责的模块 |
|---|---|---|
| 现在第几小节？ | 每个 beat/downbeat 的时间戳；弱起/变拍待确认 | Beat This! 或 all-in-one |
| 主歌、副歌在哪？ | 段落边界和功能标签；可修正 | all-in-one + 音频语言模型辅助解释 |
| 这一拍是什么和弦？ | 带起止时间的和弦候选及未知标签 | 专用和弦识别 + 人工复核 |
| 原曲贝斯实际弹了什么？ | 独立或分离声部中的音头、音尾、音高、发音类型 | Demucs + 单声部音高/转录工具 |
| 为什么这里这样弹？ | 已确认和弦、实际音符、节拍、知识来源 | 教学语言模型 + 知识检索 |
| 我能怎样 jam？ | 下一目标音、节奏约束、可达位置、风格目标 | 规则生成候选 + LLM 解释 + 指板模型校验 |

大模型生成“第 9 小节是 Am7”这句话，不能自动成为已确认的音乐事实。要能从页面跳到音频对应位置，重听并修正。不要把文字中的 BPM、和弦和时间戳当作精确测量结果。

## 3. 音频/音乐语言模型比较

| 候选 | 官方资料实际支持的能力 | 接入情况 | 本项目结论 |
|---|---|---|---|
| Qwen3.8-Omni-Flash | 当前百炼文档示范音频输入、文本输出；支持工具调用；接口名 `qwen3.8-omni-flash` | 云 API，需地域/业务空间对应配置；本轮未实调 | 云端首测候选，用于整体理解、问答和教学解释；音乐精细任务效果待测 |
| Qwen3-Omni-30B-A3B-Instruct | 官方仓库有音乐风格、节奏等 Music Analysis 示例；支持音频与文本交互 | 开源部署、vLLM、Transformers；仓库 LICENSE 为 Apache-2.0，权重与各依赖仍要按具体版本核对 | 自行部署首测候选，作为 API 路线的对照 |
| Music Flamingo (`nvidia/music-flamingo-hf`) | 官方说明包含 theory-aware captions、harmony、structure、timbre 和问答；每 30 秒处理窗口、单样本总上限 10 分钟，超长截断 | 官方说明可通过 Transformers；已核读版本为非商业研究 preview | 对目标领域很相关，但只放研究评测组；不能宣称达到逐音/逐和弦真值精度 |
| MU-LLaMA | MERT 音乐编码器 + LLaMA；音乐问答和描述 | 官方仓库提供权重获取/推理说明，依赖 LLaMA-2 7B 及较旧环境 | 早期研究基线，不优先作为新产品主模型 |
| LLark | 音乐多模态 instruction-following，代码覆盖数据处理/训练/推理 | 官方明确“not accompanied with any trained models” | 参考研究方法与评测，不能列成可直接下载上线的模型 |

注意：Qwen3.8-Omni-Flash 的云服务版本与 Qwen3-Omni-30B-A3B 的开源权重不是同一个模型，不混用性能、许可证、上下文或硬件信息。Music Flamingo 的第三方 `2601` 提法在检索中出现，但本次未读到对应官方模型卡，因此这里不采用其版本号、限制或许可做决策。

### 官方 API 的已核查要点

截至本次访问，[百炼 Qwen-Omni 文档][R01] 的文本输出示例使用 `qwen3.8-omni-flash`，输入可以是文字 + `input_audio`；示例使用流式响应。文档列出音频最长 3 小时、URL 文件不超过 2 GB、Base64 编码字符串小于 10 MB等限制。产品第一阶段仍建议只处理 30–60 秒片段，这是控制迭代成本与便于人工验收的设计选择，不是模型上限。

实际调用的 base URL 需要匹配业务空间和地域；不要把旧示例 endpoint 写死。OpenAI-compatible 接口表示协议兼容，不代表调用的是 OpenAI 模型。API Key 放后端环境变量，不能放在静态原型的 JavaScript 或导出的练习 JSON 中。

文档当前列出的 Qwen3.8 音频输入换算是约每秒 7 个 token：4 分钟音频约 1,680 个音频输入 token；文字、输出和思考 token 另计。这不是人民币费用估算，价格、限流、账号权限与可用快照需要在实际账号中确认。评测时固定模型版本并保存版本信息，避免可变 alias 升级影响结果。

### 部署成本与硬件

先用 API 做少量片段评测，能避免为了验证产品先配置大显存机器。Qwen3-Omni 的 A3B 是激活参数信息，不能理解成只需装载 3B 权重。官方 BF16 显存表是特定视频输入测试，不能直接拿来宣称纯音频的最低显存。[R02]

Music Flamingo 基于 7B 级解码器，但总开销还包括音频编码器、序列长度、KV cache 和运行框架；不能据此承诺某张 16 GB/24 GB 显卡一定能运行。实际机器与模型权重未测试前，不给最低硬件保证。

## 4. 专门分析工具的组合

| 模块 | 建议候选 | 核实到的输出/限制 | 使用方式 |
|---|---|---|---|
| 节拍与小节强拍 | Beat This! | beats/downbeats；有 CPU 回退；官方代码和发布权重为 MIT [R06] | 作为拍点基线和 all-in-one 的对照，首版无需每次双跑 |
| 曲式结构 | all-in-one Music Structure Analyzer | BPM、beats、downbeats、段落边界和 intro/verse/chorus 等标签；代码 MIT [R07] | 结构分析优先候选；Windows NATTEN 构建与旧依赖是集成成本，建议隔离环境/容器 |
| 声部分离 | Demucs / HTDemucs | drums/bass/vocals/other；原仓库明确不再维护 [R08] | 研究基线，可固定已测版本；不要把分离伪影当成原曲音符；正式版评估维护中的替代实现 |
| 和弦识别 | Chordino | 返回和弦时间和标签，支持 N；作者明确非 SOTA；GPL-2.0-or-later [R09] | 第一版离线基线，用于验证数据流；产品发布时依据分发方式核查许可证，或替换可用方案 |
| 贝斯转录 | Basic Pitch + 独立单声部音高基线 | 官方称单乐器效果最佳，可产生 MIDI；底层音高网格从 27.5 Hz 起 [R10] | 先输入 bass stem；覆盖 E1 41.2 Hz 只证明音域支持，不证明低音识别精度 |

Basic Pitch 的官方环境列表包括 Python 3.7–3.11，本机现有 Python 3.14 不应直接作为该后端环境。建议独立 Python 3.10 环境或 Linux 容器固定依赖，不修改现有系统环境。

贝斯单声部基线可进一步评估 pYIN 等方法，配置低频边界覆盖 Drop D 的 D1≈36.7 Hz。该候选本轮未单独核读实现资料，不能视为已经完成选型。短音、滑音、失真、八度谐波与 ghost note 要单独处理；ghost note 可以只记录 onset 与发音类型，不强制给 MIDI。

不要从 bass stem 单独推断完整和弦：贝斯可能弹三音、五音、踏板音或连接音。和弦识别应使用完整混音或合适的和声声部，而实际低音单独作为 `bassNote` 保存。

## 5. 产品流程与后台边界

上传/选择片段 → 解码与标准化 → 建立音频时间轴 → 结构/拍点/和弦候选 → 校对 → 映射指板 → 生成练习。

第二条可选分支：分离 bass stem → 音符候选 → 用户试听和修正 → 对比自己的编配。不要让较慢的分轨阻塞已经可用的结构结果。

音频主文件保留原采样率与声道；每个模型独立生成其要求的输入版本。所有时间戳统一映射回原音频秒数，记录重采样、裁切偏移和分离可能产生的延迟。不能用全曲平均 BPM 强行量化所有曲目；TempoMap 保留逐拍时间。

前端新增状态：`等待分析 → 解码中 → 分析中 → 部分结果 → 待校对 → 已确认`。某一步失败应保留已经成功的结果。例如结构成功、和弦失败时，仍能练段落与节奏。

页面需要新增：

1. 音频波形与可拖拽的 30–60 秒选择范围；显示原音频时间。
2. 分析进度按任务展示，支持取消与重试，不给固定的假百分比。
3. 节拍校正：半速/倍速候选、第一拍偏移、弱起和变拍标记。
4. 和弦校正：候选、未知、人工确认，支持一小节多个和弦与斜线低音。
5. 一键回听当前片段；任何教学建议都能指回它的依据。
6. “原曲贝斯”“我的编配”“仅伴奏”是三个独立模式。原曲分析更新不能覆盖用户编配。

## 6. 可落地的数据合同

`POST /api/audio-assets`：上传音频并返回 assetId、哈希和时长。

`POST /api/analysis-jobs`：输入 assetId、区间、任务集合、模型配置版本，返回 jobId。建议任务枚举 `beats,sections,chords,bass_notes,music_summary`。

`GET /api/analysis-jobs/:id`：返回各任务状态和已完成结果。推理不在浏览器主线程进行。

`PATCH /api/analyses/:id/annotations`：保存人工校正，带 revision；旧模型结果保留且可追溯。

`POST /api/coach/exercises`：只把对应片段、已确认分析、用户目标与知识卡传给模型；返回示例音符后还要经过音乐引擎校验。

一个和弦事件至少包括：

```json
{
  "id": "chord-event-001",
  "startSec": 12.4,
  "endSec": 14.9,
  "symbol": "Am7",
  "rootPc": 9,
  "bassPc": null,
  "status": "candidate",
  "source": "example-only",
  "modelVersion": null,
  "confidence": null,
  "confidenceKind": "not_calibrated",
  "userCorrected": false
}
```

以上是结构示意，不是真实歌曲分析。模型没有可用的校准概率时，confidence 保持 null；不要把大模型自报的“90%把握”转成系统概率。不同模型的原始分数也不能直接平均。

音符事件保存 `startSec,endSec,midi,articulation,sourceStem,confidence,status`；原曲推断的指法另存为候选，因为同一音高不能唯一确定弦品。教学输出保存 `evidenceEventIds,knowledgeCardIds,task,exampleNotes,uncertainties`。

缓存键由音频哈希、片段范围、模型/权重版本、预处理版本和参数组成。语义模型只在首次分析或用户提问时调用，不在每次播放器拍点变化时调用。

## 7. 教学模型的任务合同

输入：音频片段（需要听感判断时）、确认过的结构/和弦、实际 bass notes（如果存在）、乐器配置、学生当前能力、检索到的知识卡。

要求：

- 将测量结果、候选推断与编配建议明确区分。
- 不改写已确认的和弦与时间轴；发现冲突时返回冲突项与待复听区间。
- 每轮给一条练习目标、两个可比较示例和来源，不输出一整章乐理。
- 允许未知/无和弦/无可辨音高，绝不为了字段完整而填造音符。
- 生成 MIDI/拍位结构后，由确定性工具计算音名、级数与 0–21 品候选；模型不能随意声称某位置是什么音。
- 给用户的是简洁理由与证据，不需要展示模型内部思考过程。

## 8. 分阶段实现与完成门槛

### 阶段 A：真实音频的结构地图

做上传、解码、任务队列、Beat This!/all-in-one、原音频播放和段落校正。完成标准：结果确实从上传的音频产生；音频不同结果可不同；用户能听到并修正拍点和段落；失败不回退成 Night Pocket 的假分析。

### 阶段 B：和弦与指板联动

接和弦基线，展示变化区间、N/未知和候选，人工确认后才生成和弦音练习。完成标准：换和弦时间与播放同步；支持小节内换和弦；低音和根音不同的数据结构；修正后指板立即重算。

### 阶段 C：真实音乐问答与教学 Agent

接 Qwen3.8-Omni-Flash 或自行部署的 Qwen3-Omni，对真实音频做整体描述，并使用阶段 A/B 的证据解释段落与落点。完成标准：返回证据引用、未知项和可执行练习；对同一音频换问题能回答不同内容；无法听清时允许拒答。

### 阶段 D：原曲贝斯与 jam

加入分离、低音转录、原曲/编配对比、节奏与音长编辑；用同一已确认和弦生成“简洁/有连接/有留白”的候选。完成标准：可比较的实际音符数据与音频，不把一段自然语言描述当成转录。

优先完成 A+B 才能满足用户“跟着结构和和弦 jam”的硬需求；单独上线 C 只会得到一个能聊音乐的界面。

## 9. 评测计划：如何判断哪个模型真的适合

准备第一批 24 个合法可用的 30–60 秒片段，每类至少 4 个：流行/摇滚直八、funk 切分、慢速长音、shuffle/swing、转位/斜线和弦、复杂混音/失真/弱起等困难片段。教师标注拍点、段落、和弦和可辨贝斯事件，保留多解与争议。

| 任务 | 评价方法 | 不接受的替代指标 |
|---|---|---|
| 节拍 | beat/downbeat F1，检查半速倍速；报告容差（如 70 ms） | 只比较平均 BPM 是否接近 |
| 段落 | 边界 F1（如 0.5 s 与 3 s 两档）与标签质量 | 只说“模型认为有主歌和副歌” |
| 和弦 | 按时间加权的正确率，root/major-minor 与 seventh/inversion 分开 | 只看文字解释听起来是否专业 |
| 贝斯音符 | onset/pitch F1、八度错误率、时值误差，听辨伪影 | 把输出 MIDI 数量当作完整度 |
| 教学 | 两位教师盲评事实正确、可演奏、难度适配、证据支持 | 用用户满意度代替事实正确性 |
| 不确定性 | 错误自信率、弃答率与覆盖率曲线 | 给所有输出都附同一个 confidence |

上述容差是评测设置建议，不是已经取得的分数。先拿到基线结果再设置上线门槛；按音乐风格与音源质量分层报告。一次跑通 API 不等于功能验收通过。
